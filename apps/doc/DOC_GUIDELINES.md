# 文档写作规范

本文档是 `apps/doc/web` 下中英文使用指南的写作规范。目标是让指南成为**引导用户逐步掌握引擎的教程**，
而不是 API 说明书——属性和签名的枚举交给 TypeDoc 自动生成的 API 参考（`/api/`），指南只讲
**为什么、什么时候用、怎么取舍**。

## 站点结构速查

改文档前需要知道的机制，细节见 `web/.vitepress/config.mts`：

- 站点是 VitePress，首页是 `web/index.md`。
- **侧边栏由 `web/{en,zh-cn}/_sidebar.md` 生成**（`config.mts` 里的 `parseSidebar()` 解析这两个
  docsify 风格的缩进列表）。新增或移动页面必须同步改这两个文件，且两边结构保持对称。
- 正文里的 `/doc/markdown/./scene.xxx` 形式的 API 链接由 `normalizeDocLink()` 在渲染期重映射到
  TypeDoc 产出的页面。这是有意保留的兼容层，**不是死链，不要批量改写**。
- API 参考由 TypeDoc 从库源码直接生成，不要手写。
- `_sidebar.md` 之外的下划线开头文件会被 `srcExclude` 排除，不会构建。

## 一、代码示例：单一真相源

**这是本规范最重要的一条。**

可运行示例的源码在 `apps/doc/src/tut-N/main.js`，通过
`<div class="showcase" case="tut-N"></div>` 嵌入页面。该 iframe 已经会拉取并高亮 `main.js` 的
真实内容，所以**在 markdown 里手抄一份代码就等于制造第二份真相源**——历史上这两份已经漂移，
出现过漏 import、正文与代码矛盾、调用不存在方法等问题。

因此：

### 教程式页面（有对应 `tut-N` 的完整流程）

用 VitePress 的代码片段导入，不要手抄：

```md
<!-- 整个文件 -->
<<< @/../src/tut-5/main.js{js}

<!-- 只引某一段（行号区间） -->
<<< @/../src/tut-5/main.js{24-30 js}
```

路径以 `web/` 为基准，所以 `@/../src/...` 指向 `apps/doc/src/...`。

需要讲解某一段时，优先"先引片段、再在正文解释"，而不是把代码复制进正文加注释。

> 已知取舍：`src/tut-*/main.js` 里的注释是英文的。中文页引用后注释仍为英文。
> 处理方式：**不要**为此复制一份中文代码（那会重新制造漂移），而是在正文用中文讲解关键行。
> 若某段注释确有必要中文化，改 `src/` 里的源码，让两边同时受益。

### 片段式页面（讲解某个特性，无完整流程）

这类页面（如 `lighting-*`、`user-material-*`、`oit`、`sky`）按既有约定不写 import，只给关键调用。
这是可以的，但**必须在页面开头声明**，避免用户误以为可以直接复制运行：

```md
> 本页代码为片段示意，省略了 import 与应用初始化。完整可运行示例见页内嵌入的实例。
```

如果片段用到了名字不直观的符号，在正文说明它来自哪个包（`@zephyr3d/base` 还是
`@zephyr3d/scene`）。

### 硬性要求

- 引用的 `case="tut-N"` 必须在 `apps/doc/src/` 下真实存在。
- 代码中出现的每个引擎符号都必须真实存在。写完新增或改动的代码后，用
  `grep` 在 `libs/*/src` 或 `apps/doc/report/*.api.md` 里确认，尤其是方法名和参数顺序。
- 正文描述与代码必须一致（例如别写"创建正方体"却 `new SphereShape()`）。

## 二、页面结构：四段式

新写或改写页面时用这个骨架，避免退化成属性清单：

1. **这是什么、解决什么问题**（1–3 句）
   用户为什么需要它。不要写"本节介绍 XXX 的用法"这类空话。

2. **最小可跑例**
   能看到效果的最短路径，配 `<div class="showcase">` 实例。

3. **调参与取舍**
   常用参数的**作用与影响**，以及在什么场景下该怎么选。这里是指南的核心价值，
   也是与 API 参考的分界：API 参考给类型和默认值，指南给判断依据。

4. **限制与坑**
   后端差异（WebGL/WebGL2/WebGPU）、性能代价、与其他特性的冲突、静默回退行为。
   有能力门控的（如 WebGPU-only、需要 `supportShaderF16`）必须写明检测方式。

参照样板：`asset-loading.md`（准确、讲清了 prefab 与直接加载模型的取舍）、
`scene-basic.md`、`shader.md`（有生成结果对照）。

## 三、写作风格

- **讲取舍，不堆属性。** 罗列十个属性不如说清"什么情况下该调哪个、调了会牺牲什么"。
- **不写营销话术。** 不要"产品特色""应用场景""技术支持与社区"这类段落，也不要
  "强大""极致""业界领先"。指南读者已经决定要用引擎了。
- **不重复。** 概述性内容集中在 `intro.md`，其他页不要再介绍一遍引擎是什么。
- **表格用于对照，不用于替代解释。** 三个模式怎么选、两个 API 字段有何不同——适合表格。
  单个类的方法清单——不适合，交给 API 参考。
- 中文与英文之间、中文与代码/符号之间不强制加空格，与既有文档保持一致即可。
- 术语统一（下节）。

## 四、术语

| 概念 | 中文用法 | 说明 |
| --- | --- | --- |
| Device API / Scene API | 保留英文 | 指两套 API 层，不译 |
| shader | shader 或 着色器 | 同一页内统一 |
| Mesh / Material / Primitive | 网格 / 材质 / 图元 | |
| SceneNode | 场景节点 | |
| prefab | 预制体 | 统一用"预制体"，不要混用"预制件" |
| bind group | 绑定组 | |
| pass | pass | 不译，如 DepthPass、LightingPass |
| tonemap | 色调映射 / Tonemap | 标题可用英文，正文用中文 |

引擎的类名、方法名、属性名一律保留英文原样，用反引号包裹。

## 五、中英同步

- 两棵文档树 `web/en` 与 `web/zh-cn` **页面集合必须一致**，`_sidebar.md` 结构必须对称
  （仅语言与路径前缀不同）。
- 当前流程是中文先行、英文跟进。改动涉及事实性内容（API 名、签名、限制）时，
  **两边必须同时改**，不能只改一侧。
- 只改措辞时可以分开提交，但不要让两边的技术内容出现分歧。

## 六、提交前自查

- [ ] 代码里的符号都在源码中确认存在，参数顺序核对过
- [ ] 引用的 `tut-N` 存在，片段导入路径正确
- [ ] 正文与代码不矛盾
- [ ] 中英两边同步，`_sidebar.md` 两边对称
- [ ] `npx vitepress build web` 构建通过
- [ ] 新增页面已加入两个 `_sidebar.md`
